# Voice call — contract and flow

The owner's decision (P391): support Codex's `/voice` the way Codex does it — a **voice call
with the thread**. The user talks; a realtime speech-to-speech model talks back and hands work
to the thread by starting or steering ordinary turns. This is a **separate feature from
dictation** ([voice.md](voice.md)): dictation puts words in the composer and never acts; a
call acts in the thread.

This file is the **shared contract** between yaacd, the hub, `yaac-core`, the window
controller and the renderers (Android first). The Rust types in
`crates/yaac-protocol/src/types/voice_call.rs` are its source of truth; the TypeScript in
`daemon/src/protocol/generated/` is generated from them, never hand-edited.

## What Codex does (verified, codex-cli 0.172.0)

Read from `codex app-server generate-ts --experimental` and the tagged source `rust-v0.172.0`
(`app-server/tests/suite/v2/realtime_conversation.rs`, `tui/src/app_server_session/realtime.rs`,
`tui/src/realtime_call.rs`). See also
[harness surfaces](../research/harness-surfaces.md#the-webrtc-transport-verified-2026-11-27-for-a-chatgpt-sign-in).

- `thread/realtime/start { threadId, outputModality: "audio", transport: { type: "webrtc",
  sdp }, version: "v3" }` → `{}`. The `sdp` is "an SDP offer generated by a WebRTC
  RTCPeerConnection after configuring audio and the realtime events data channel". Codex posts
  it to its realtime calls endpoint **with its own auth** (works for a ChatGPT sign-in), then
  emits `thread/realtime/started { threadId, realtimeSessionId, version }` and
  `thread/realtime/sdp { threadId, sdp }` (the answer), and joins the call through a
  server-side sideband websocket.
- **Media flows between the client's peer and OpenAI over RTP.** No audio passes through
  Codex, yaacd, the hub or the window controller.
- WebRTC needs a conversational session, version v1 or v3 (v2 is refused). The TUI uses v3
  (with `existingCall` because it creates the call itself; YAAC hands Codex the offer
  instead, which Codex's own tests cover for v3). The realtime model answers aloud and its
  delegations start or steer a turn **in that thread**.
- `thread/realtime/transcript/delta { threadId, role, delta }` and `…/done { threadId, role,
  text }` (`role`: `user` | `assistant`) carry what is said. `thread/realtime/error
  { threadId, message }`, `thread/realtime/closed { threadId, reason }`.
  `thread/realtime/stop { threadId }` ends it.
- `model` and `voice` stay unset: Codex picks them (invariant 3).

## Consent

A call **acts in the thread**: what the model hands off becomes turns that run with the
thread's own approval policy and sandbox, and the realtime model's audio is charged to the
user's Codex sign-in (ChatGPT plan or API key). The button says so the first time
("Talk with this thread — it can start work here, using your Codex plan"). Turns the call
starts are ordinary turns: journaled, shown, interruptible, and their approvals reach the
user as always (invariant 8). A message from the call is never presented as an agent mesh
message.

## Rules that do not bend

- **No audio touches YAAC.** Only SDP text and transcript text cross the wire. Nothing about
  the call's media is logged; transcripts are not journaled by YAAC (Codex records what it
  records in its own thread).
- **One connection per target** (invariant 1): signalling is JSON-RPC on the existing stream.
  The media connection is the client's own, to OpenAI — not a connection to a target.
- **Capabilities, not kinds** (invariant 4): the call button shows iff the thread's effective
  capabilities contain `voiceCall`.
- **One writer** (invariant 9): a thread in use elsewhere (read-only) cannot start a call;
  `voiceCall/start` is refused with `thread_in_use`.
- **No blind retries** (invariant 10): `voiceCall/start` carries an `opId`; an uncertain start
  is shown, not re-sent.
- **Codex's daemon is never stopped or restarted** for a call (invariant 11).

## Capability and feature

| Where | Name | Meaning |
| --- | --- | --- |
| `initialize` → `features` | `voiceCall` | This `yaacd` implements `voiceCall/*`. Without it the hub's dialect folds `voiceCall` out of every capability set. |
| `ProviderDescriptor.capabilities` | `voiceCall` | The harness has the realtime WebRTC surface (Codex: the app-server answers `thread/realtime/listVoices`). Any sign-in type. |
| `ThreadEffective.capabilities` | `voiceCall` | This thread can start a call now. No format: media does not pass through YAAC. |

## Methods (yaacd ⇄ host, additive feature `voiceCall`)

| Method | Direction | Params → Result |
| --- | --- | --- |
| `voiceCall/start` (op) | host → daemon | `VoiceCallStartParams { opId, threadId, sdpOffer }` → `VoiceCallStartResult { callId }`. Answered once Codex accepted `thread/realtime/start`; every notification below for this call comes after the result. |
| `voiceCall/end` | host → daemon | `VoiceCallEndParams { callId }` → `{}`. `voiceCall/state ended` follows. Ending an unknown or ended call is not an error. |
| `voiceCall/answer` | daemon → host | `VoiceCallAnswerParams { callId, sdpAnswer }`. Once per call. The client sets it as the remote description. |
| `voiceCall/state` | daemon → host | `VoiceCallStateParams { callId, state, error? }`. `state`: `connecting` (start accepted, waiting for the answer) → `active` (answer sent) → `ended`. `ended` is always the last message for a call; `error` is words for the user, absent after a normal end. |
| `voiceCall/transcript` | daemon → host | `VoiceCallTranscriptParams { callId, role, text, final }`. `role`: `user` \| `assistant`. `text` is the **whole** current utterance of that role and **replaces** the previous `text` for that role; `final: true` closes the utterance, and the next message for the role starts a new one. |

`callId` is an opaque string chosen by yaacd, unique on its target.

`voiceCall/start` errors: `capability_missing`, `thread_not_found`, `thread_in_use` (read-only
here, invariant 9), `limit_exceeded` (a call is already running on this thread — one per
thread), `provider_unavailable` (Codex refused: message carries its words), `needs_auth`.

yaacd ends a call by itself (`voiceCall/state ended` with `error`) when Codex reports an error
or closes the session, when its connection to Codex drops, and — without telling anyone, since
nobody is left — when the host connection that started it drops. Turns the call already
started keep running (invariant 8).

## Attach protocol (window ⇄ hub)

Target-side params flattened beside `target` (`TargetVoiceCall<P>` = `{ target, ...P }`);
`callId` is passed through unchanged (it is already target-unique; the window keys calls by
`(target, callId)`).

| Name | Direction | Payload |
| --- | --- | --- |
| `hub/voiceCall/start` | window → hub | `{ target, opId, threadId, sdpOffer }` → `{ callId }` |
| `hub/voiceCall/end` | window → hub | `{ target, callId }` → `{}` |
| `hub/voiceCall/answer` | hub → the starting window only | `{ target, callId, sdpAnswer }` |
| `hub/voiceCall/state` | hub → the starting window only | `{ target, callId, state, error? }` |
| `hub/voiceCall/transcript` | hub → the starting window only | `{ target, callId, role, text, final }` |

The hub keeps only the `(target, callId) → window` mapping; it caches no SDP and no words. If
the window disconnects, the hub sends `voiceCall/end`. If the target connection drops, the hub
sends the window `hub/voiceCall/state ended` with an error. `voiceCall/*` is refused through
`hub/request` ("use the hub voice call methods").

## Window controller (shared by egui, WPF, Android)

The composer frame of a thread whose effective capabilities contain `voiceCall` carries a
`call` object (absent otherwise):

```jsonc
"call": {
  "state": "idle" | "starting" | "connecting" | "active" | "ending" | "error",
  "callId": "…",              // once known
  "answer": "v=0…",           // the SDP answer, once it arrived, until the call ends
  "error": "…",               // the last failure on this thread, until the next start
  "transcript": [             // the last 50 utterances, oldest first
    { "role": "user" | "assistant", "text": "…", "final": true }
  ],
  "status": "…",              // one line for the renderer
  "button": { "id": "composer.callStart" | "composer.callEnd", "label": "…", "enabled": true, "detail": "…" }
}
```

Commands (renderer → controller):

| Command | Params | Effect |
| --- | --- | --- |
| `composer.callStart` | `{ key, sdpOffer }` | Starts a call on `key` with the renderer's offer. Needs the composer writable and no other call in this window. |
| `composer.callEnd` | `{ key }` | Ends the call. Always allowed. |

**Where it lives (answers for the renderers).**

1. `call` is a field of the **composer frame of a thread** (the same object that carries
   `voice`), so it is per thread key: the composer for key K shows K's call. A draft for a new
   thread has no `call`.
2. The SDP answer is **state in that frame, not a one-shot effect**: `call.answer` (a string)
   appears once the answer arrives and stays until the call leaves `connecting`/`active`, so a
   renderer that re-subscribes or restarts still gets it. Apply it **once per `callId`**
   (remember the last `callId` you applied).
3. The capability shows to renderers as **the presence of `composer.call`**: present iff the
   thread's effective capabilities contain `voiceCall`. Renderers never look at the provider.

The **renderer** owns the media. Verified by C2 in `openai/codex` rust-v0.172.0
`voice-host/src/transport.rs` (Codex's own peer): one Opus send track plus receive, a data
channel labelled `oai-events` with default options, a **non-trickle** offer (wait for ICE
gathering to complete, up to 15 s), no ICE servers, and the call counts as ready when the data
channel opens. Do the same: create the `RTCPeerConnection` with the microphone track and the
`oai-events` data channel, make the offer, wait for gathering, send `composer.callStart` with
the complete SDP, apply `call.answer` as the remote description, play the remote audio track,
and close the peer when `call.state` leaves `connecting`/`active` (or on `composer.callEnd`).
The data channel carries Codex's realtime events between the peer and OpenAI; the renderer may
ignore its messages (transcripts reach it through `call.transcript`).

One call per window. Leaving the thread does **not** end a call (it is a conversation with the
thread, not with the composer); the thread's composer keeps the call controls. While a call is
active in a window, that window offers no dictation (the microphone is the call's).

## Implementation notes

- yaacd: `daemon/src/voice/calls.ts` (registry: call id, one per thread, result before any
  notification, `ended` last, hang-up on a dropped connection) and
  `daemon/src/providers/codex/voice-call.ts` (the Codex driver). Turns that start while a call
  is live are recorded as the user's own ([04](../04-providers.md#voice-call-codex)).
- Hub: `crates/yaac-hub/src/core/voice_call.rs`; the result and the notifications share the
  window's terminal lane, so the result arrives first.
- `yaac-core`: `voice_call.rs` and `Client::voice_call_start / voice_call_end / voice_call /
  take_voice_call_outcome`. Controller: `crates/yaac-app/src/voice_call.rs` (`start` returns
  the refusal, which also shows as `call.error`). No dictation while a call runs in the window,
  and no call while dictating (the microphone is one).
- The demo hub scripts a call (connecting, answer, active, one line each way, ended on
  `callEnd`). Its answer is **not real SDP**: a demo renderer's peer cannot connect, so a
  renderer should not open the microphone against the demo.

## Flow

```
renderer           controller/yaac-core        hub              yaacd                 Codex app-server
createOffer ──callStart{key,sdpOffer}──▶ hub/voiceCall/start ─▶ voiceCall/start ─▶ thread/realtime/start{webrtc,sdp,v3}
                                                                  ◀── {} ─────────────
                 ◀──── {callId} ◀────────── {callId} ◀────────
                 ◀── state connecting ◀──────────────────────
                                                                  ◀── realtime/started, realtime/sdp
                 ◀── answer{sdpAnswer} ◀──── voiceCall/answer ◀──
setRemoteDescription                         state active
⇄ RTP audio with OpenAI (not through YAAC) ⇄
                 ◀── transcript ◀──────────── voiceCall/transcript ◀── realtime/transcript/{delta,done}
                                             (turns the model starts arrive as ordinary thread events)
callEnd ───────▶ hub/voiceCall/end ───────▶ voiceCall/end ──────▶ thread/realtime/stop
                 ◀── state ended ◀──────────────────────────── ◀── realtime/closed
```
