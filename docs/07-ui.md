# 07 — UI

## Stack

- **Rust**, `eframe` + `egui`, GPU-accelerated. Backend (`glow` or `wgpu`) chosen by
  measurement in spike S1; see [footprint](02-architecture.md#footprint-budget).
- Markdown through a `pulldown-cmark`-based renderer (`egui_commonmark` or our own on the same
  parser), with code highlighting loaded lazily.
- No web view, no JavaScript in the host.

## Design principles

Three decisions by the owner, made on seeing the first mockups, govern everything visual:

0. **Monochrome.** There is no accent colour. Colour appears only where it carries meaning:
   needs you (a red exclamation, D113), failed, done, git changes, and — as an outline only —
   a turn that finished unseen (cornflower blue, D114).
1. **Calm before complete.** Every mark on screen must earn its place. The sidebar is a flat
   list, not a tree.
2. **Local time.** Every time shown or entered uses the time zone of the computer the window
   runs on, never the target's.
2. **No outlines.** Controls are not boxed. Things are told apart by space, then by a faint
   fill, and by a line only where two regions meet.
3. **The conversation comes first.** In a chat, what the user and the agent say to each other
   is the content; everything else is quiet.

The exact rules, colours, and every screen are in [design/screens.md](design/screens.md).

## Sidebar

**Decided: a flat list under sticky headers — not a tree.** No indentation, no chevrons, no
folder icons, no nested levels.

- **Rows (decided: two lines).** Line 1: a state mark, the title, and on the right a relative
  time. Line 2, smaller and quieter: a branch icon and the **git branch**, then — very
  compactly, with real icons and the usual git colours — how the thread's checkout differs
  from origin: files **added** (green), **modified** (soft yellow), and **deleted** (red),
  then commits not pushed and not pulled; each shown only when it is not zero. The count of direct workers,
  when there are any, sits at the **right edge of line 2**, under the time. Icons come from one small embedded icon set,
  never from Unicode symbols. A thread whose folder is not in git has a one-line row. Each state has its
  own shape, so the mark reads without a word beside it.
- The git line comes from the target: `yaacd` asks git once per checkout, not per thread,
  caches the answer, and refreshes it when a turn ends in that checkout and on a slow timer
  for rows that are on screen. It is never refreshed for the whole fleet at once. Counts compare
  the working tree, untracked files included, with the point where the branch left its
  upstream — so other people's pushes do not show up as your changes.
- **The PR badge** (D119, moved to line 1): at the right of the title line, **before the
  relative time** — the title ellipsizes first, so the badge and the time stay whole. An
  almost square, monochrome box: `PR#` and the number of the branch's open pull request
  (`[ PR# 33342 ]`), `+N` when the branch has more (`[ PR# 33343 +1 ]`; hovering `+N` lists the
  others, each clickable), or a blank number (`[ PR#      ]`) when there is none yet. Click
  opens the pull request in the host's default browser, or the **Create PR modal**; right-click
  offers **Create a new PR** and **Copy link** (and asks the target again). Hints (P48): dashed
  outline for a draft, a merge mark for merged, a struck-through number for closed, a small cross
  when checks fail, a dotted ring while they run. No badge outside git, on a remote that is not
  on a supported forge, or on the default branch with no pull request; with `gh`/`az` missing
  or signed out, a lock and the reason on hover. The docked panel's rows carry the same badge.
- **Create PR modal** (D120): *Into* (target branch, default the repository's default branch,
  from the remote's branches), *Title* and *Description* prefilled from the branch's commits
  and editable, **Draft**, and **Ask the agent to write it** — a message to the thread's agent
  (it costs a turn) whose reply fills title and description (P50). When the branch has unpushed
  commits or no upstream, a notice says Create will push it first; uncommitted changes are only
  warned about. An uncertain create is shown as such and never repeated.
- **Section headers.** One quiet line naming the group — the project on the left, the machine
  on the right — pinned to the top of the list while its rows scroll beneath it. Because each
  row carries its branch, sections are per project by default; the worktree level can still
  be ticked on to split them. A
  connection mark appears beside a machine only when it is *not* connected.
- **Grouping.** The three levels — machine, project, worktree — are still independently
  switchable ([grouping rules](05-threads.md#sidebar-grouping)); they are three checkboxes in
  one small menu on the search field. What is ticked makes up the header text. With nothing
  ticked there are no headers: just the list.
- **Ordering** (D116): an icon beside the grouping control opens a menu — **Last message**
  (default), **A → Z**, **Z → A** (by title, case-insensitive, natural order), and two
  checkboxes, both on by default: **Keep unseen finished threads at the top** and **Keep
  threads that need you at the top**. The order applies inside each group, in *Pinned*, and in
  the plain list; floated threads sit at the top of their group (needs you first, then unseen,
  each in the chosen order) and drop back once answered or seen. While the pointer is over the
  list, or a row's menu is open, a reorder is held back until the pointer leaves, so a row
  never moves away under it. A window preference, stored like the grouping.
- **There is no Needs-you section** (D116). Every thread waiting on the user — an approval, a
  question, a permission, a budget — floats to the top of its group and carries the red
  exclamation. The **Needs-you button** (D117), the same red exclamation with a count beside
  the back and forward buttons (and under them in the strip), is shown only while some thread
  needs the user; each press opens the next one, cycling through those still unresolved, most
  recent first. **Ctrl+J** does the same. Tooltip: "Next thread that needs you (N)".
- **Pinned** is the first section: threads the user pinned, from any project. Hidden when
  empty. A pinned thread is listed here instead of under its project.
- **Project sections** follow. A project shows the name the user gave it. A **temporary
  project** — a folder with discovered threads but no project yet — is shown in italics with
  a dashed mark and its folder path; right-clicking its header offers **Create project…**,
  with the folder prefilled and editable ([projects](05-threads.md#projects)).
- **Muted** is the last section, collapsed to its header. Muted threads keep working; one that
  becomes blocked is listed in its group (at the top) until answered. Muting asks for how
  long: until unmuted, for a number of minutes, hours, or days, or until a chosen date and
  time — a date field with a calendar button that opens the calendar as a dropdown, always six
  week rows so it never changes size (D112); a timed mute ends by itself.
- **Archived** comes after *Muted*, also collapsed to its header — "Archived · 12" — and lists
  archived threads when opened; Unarchive is in each row's menu. It replaces the earlier "Show
  archived" switch. **Archiving a thread removes its pin and its mute**: an archived thread is
  only ever in *Archived*.
- **Right-click a row** for the thread menu (D109): **Copy thread ID, Rename** — separator —
  **Fork, Pin / Unpin, Mute… / Unmute, Archive…** (Unarchive on an archived row) — separator —
  **Delete…** in the destructive colour; on a thread outside any project, **Dismiss**, which
  just hides it ([details](05-threads.md#dismissing-a-discovered-thread)). Rename, Archive and
  Delete's harness option follow the thread's capabilities. While the menu is open the row
  keeps its hover colour (D108). **Archive…** asks for confirmation in a modal (D111).
  **Delete…** opens "Delete *title*?" with **"Also delete the session from *harness*"**,
  checked by default and shown only under the `threadDelete` capability (D110); YAAC's own
  record and journal always go. The request carries an operation id; a lost answer is shown
  as an unknown outcome and never re-sent. Once deleted, the thread leaves the list, the
  history, and the view preferences.
- **A finished turn nobody looked at** (D114): when a thread's (or a subagent's) turn ends and
  no window shows that thread, the hub marks it *unseen* — a view preference beside pin and
  mute, so it survives a restart and every window agrees. The row gets a cornflower rounded
  outline (sidebar, docked panel), a ring around its icon (pill, strip). Opening the thread
  clears it. Needs you, paused, failed and running take precedence: while one of those marks
  shows, the outline is not drawn. It is not part of *Needs you*.
- **A narrow row keeps every mark** (D115): the title — and the branch on line 2 — is
  ellipsised; the state mark, harness logo, git counts and ahead / behind stay. Archived threads
  leave the list; a "Show archived" switch in the same menu as the grouping brings them back,
  and search always finds them.
- **The selected row is always the open thread**, drawn as a tint so everything on it stays
  readable.
- **Needing the user outranks every other state.** A thread with a pending request shows
  *needs you*, not *running*. That is the thread's own state; its parents carry no mark for it.
- A machine whose daemon is on an older version carries a warning mark; its tooltip says
  *"Running an older YAAC daemon — it will be updated when idle"*, with **Update now**
  ([09 Compatibility](09-compatibility.md#upgrading-a-daemon-without-interrupting-it)).
- **A WSL distro that is down** raises a notification with one action, **Start it**. Its
  threads stay listed but are disabled — readable, with the composer replaced by "Ubuntu is not
  running · Start it" — and become responsive again once the distro is up. YAAC never starts a
  stopped distro on its own.
- An offline machine's threads remain visible from cache, with "offline" beside the machine.
- Only recent threads are listed: discovery is capped by age and number
  ([details](05-threads.md#discovery-is-capped-by-age-and-by-number)). A project section ends
  with "Show older" when the target has more, and search offers "Search older threads on
  *devbox*".
- **Back and forward** buttons beside the title step through the places the user has been —
  threads, settings, drafts — like a browser, each remembering its scroll position. Holding or right-clicking a button
  lists the places in that direction, to jump several steps at once. The
  mouse's back and forward buttons and Alt+← / Alt+→ do the same.
- Search filters by title and preview across the cached index — no round-trip. It matches
  fuzzily, and also finds a thread by its id or the start of it.
- A row's right-click menu has **Copy thread ID**, so a thread can be named to another agent: "tell
  thread 0198a1c4 on devbox when you finish".
- **New** at the top is the one way to start a thread (D107): the draft opens in the main
  area and is not listed as a row in the sidebar.
- The footer holds Settings and a quiet **hub status** (D106): a connection icon in a muted
  colour — crossed out while the hub cannot be reached — then the targets as counts only: an
  up arrow with the number connected and a down arrow with the number not connected (the
  down count is hidden when it is zero).
- **The sidebar is resizable** by dragging its edge, and **collapses into a vertical strip**
  (button, Ctrl+B, or dragging past its minimum): the YAAC mark, a + button, the history
  buttons side by side, each project's name written vertically (Pinned as a pin icon) with one
  harness logo per thread carrying its state as a corner badge (the red needs-you exclamation
  when it needs the user, a cornflower ring when its turn ended unseen), a hairline between projects, and Settings (D103). Hovering an icon shows the full row in a floating card; the wheel scrolls the
  strip. A narrow window collapses to the same strip by itself.

With the window closed, the hub raises a desktop notification for anything that needs the user;
it opens the exact request.

## Thread view

- A virtualised list of items: only what is on screen is laid out and painted.
- **Decided: the conversation comes first.** Only the user's messages and the agent's prose
  are full size. Everything else is *activity* — reasoning, tool calls, messages to and from
  other agents, workers being started, waiting — and is shown **collapsed by default as one
  muted line**: `Ran cargo test — passed`, `→ CI integration · delivered`,
  `← billing-service · Migration merged. 14 tests…`.
  - Consecutive activity lines sit tight together as one quiet run; a long run folds into a
    single summary line that expands to the lines.
  - Clicking a line expands its detail in place — the command and its live output, the whole
    message with its receipt — still drawn muted.
  - A failure stays one line but keeps the failed mark and colour, so it is noticed unopened.
  - What needs the user is never collapsed: approvals, questions, the permission prompt, and
    the budget notice are the only cards in a transcript.
  - In a thread an agent started, the message that set its task is shown in full where a user
    message would be, labelled with who sent it.
- Agent text streams in as markdown. Code blocks have a copy button. File changes are diffs:
  a collapsed line with `+12 −3` that expands to a unified diff, and one summary line at the
  end of a turn that changed files.
- **All text can be selected and copied**, including one selection across several items.
- Pending `request` items render inline as an approval or question card and also raise the
  thread's attention state in the sidebar. An approval card shows the decisions the harness
  actually offers, not a fixed Allow/Deny pair. A question card shows each question with its
  options, multi-select where allowed, and a free-text answer where allowed; a secret answer is
  masked. Cards also show what happened next: *submitted*, then *confirmed — answered by
  you* once the agent acknowledges it; and the quieter outcomes *resolved elsewhere*, *expired*,
  and *outcome unknown*, which offers "Check latest status" and never a resend
  ([request states](03-protocol.md#request-states)). A secret answer is masked while typed and
  in every summary afterwards.
- **A thread in use elsewhere is read-only.** The transcript keeps updating, a banner says
  where it is in use ("in use in another program", "in use on *laptop*"), the composer is
  disabled, and request cards are shown without their buttons. Fork stays available
  ([05 Threads](05-threads.md#in-use-elsewhere)).
- A forked thread shows its inherited history above a divider, read-only.
- Sticks to the bottom while streaming unless the user has scrolled up.
- Header shows the state mark and title (editable under `ThreadRename`), origin, project, and
  worktree, and — for a thread with relatives — a line of links: *spawned by*, *forked from*,
  or the full ancestry for a worker several levels down.

## Agents in the thread view

**Decided:** the thread view shows the sub-threads of the open agent in a side panel, and the
chat shows messages between agents — naming who they went to and who they came from.

### The agents panel

**Decided: three states, smallest first.** It answers "who is this agent working with, and how
is each of them doing?" — and by default it does so in 44 pixels. It exists only for a thread
that has a parent, workers, or contacts.

| State | What it is | Shows |
| --- | --- | --- |
| **Pill** (default) | A narrow vertical pill floating over the right edge of the thread. | One harness icon per related agent, in three fixed clusters (D118) — spawned by, workers, in contact — each headed by a tiny muted glyph (an up arrow, a branch, ⇄) and separated by short hairlines; an empty cluster and its hairline are not drawn. A small arrow beside an icon while data is moving: up for sending to that agent, down for receiving from it. The red exclamation on an agent that is blocked on the user, a cornflower ring on one whose turn ended unseen. Finished agents dimmed. |
| **Card** (hover or focus) | The pill widens into a floating card over the transcript; the layout does not move. | "Related agents": each agent as a row — icon, name, one ellipsised line with the last thing it did — under the docked panel's three headings (D118). A dock button. |
| **Docked** | Pinned to the side as a fixed panel; the thread narrows. | "Related agents" (D115): the same rows under three quiet headings — *Spawned by*, *Workers*, *In contact with* — and the orchestration's budget. Each row: state mark, title, state word; harness logo, branch, git counts; provider · model · target; latest activity. Narrow, the title ellipsises and every mark stays. The thread menu on right-click. An undock button. |

The card, the docked panel and the pill draw one grouping from core
(`yaac_core::agents::clusters`), so they always agree.

In every state an icon or row opens that thread. The docked panel is drawn in the same muted
style as the rest: no boxes, no rules, names as links. Whether it is docked is remembered. Docked, it is **resizable** like the sidebar (D105): its
hairline is a drag handle, between 240 and 520 points, and the width is remembered.

The arrows are the one piece of motion in the interface, and they are tied to something real:
an arrow is shown only while a message or a result is actually in flight, and it repaints only
then — an idle fleet still costs no CPU.

When an orchestration's [budget](10-agent-mesh.md#every-orchestration-has-a-root-and-a-budget)
runs out, the root thread shows a notice — nothing was cancelled, how many messages are
waiting — with one primary action, **Continue**, and counts as needing the user (it floats to the top
of its group and the Needs-you button includes it).

### Agent messages in the transcript

Four item kinds. All of them are *activity*: one muted line each by default, with the detail
below shown when a line is expanded:

| Item | Looks like | Shows |
| --- | --- | --- |
| **Sent** (`meshSent`) | `→ CI integration · delivered` | **To** *title · provider · target*, the text, and a receipt: delivered, or queued with the reason. |
| **Received** (`meshReceived`) | `← billing-service · Migration merged…` | **From** *title · provider · target*, the text. Never styled like a user message — it did not come from the user. |
| **Workers** (`meshSpawn`) | `Started 3 workers · 2 of 3 finished`, updated in place | "3 workers · 2 of 3 finished", and for each: state, title, provider, model, target, latest activity. Each row is a link. |
| **Waiting** (`meshWait`) | `Waiting for search-service…` | What the agent is waiting for. |

The name in a **To** or **From** line is a link to that thread, so a conversation can be
followed from either end. A receipt says what it means: *"Delivered — stored in its mailbox"*,
or *"Queued — staging is offline. It will be delivered when staging reconnects."*

## Composer

- **Multi-line text input (decided).** The composer is **two lines tall when empty**, so it
  reads as a place for more than one line. **Shift+Enter** starts a new line; Enter sends. As
  the text grows the composer grows with it, **up to five lines**; beyond that its height stays
  put and the text scrolls inside it, with a scrollbar. Wrapped lines count as lines. It
  shrinks back as text is removed, and returns to two lines after sending. The transcript
  keeps its place while the composer changes height.
- **Markdown in the composer (decided): styled as you type.** Emphasis, headings, inline code,
  and fenced code blocks are visibly formatted in place, and the markdown characters stay
  visible and editable. It is one plain-text editing surface, so the caret, selection, undo,
  and input-method composition behave exactly like a normal text box. Formatting work is
  bounded, so pasting a very large text does not stall typing.
- **Enter and input methods.** While an input method is composing (Japanese, Chinese, Korean,
  dead keys), Enter confirms the composition and never sends the message.
- **Paste and drop** files and images; each becomes a chip with upload progress
  ([06 Attachments](06-attachments.md)).
- **While a turn runs, a message can be queued or sent now** (decided — the same choice an
  agent has through the mesh tools):
  - **Enter queues it.** The message waits and is delivered when the running turn ends. It is
    held by the daemon, not by the window, so it is delivered even if the window is closed.
    Queued messages sit in a small strip above the composer, in order. Each has **Send now**,
    which stops it waiting and sends it at once (steering or interrupting, exactly like
    Ctrl+Enter), and can be edited or cancelled, until it is delivered.
  - **Ctrl+Enter sends it now.** Where the harness can steer, the message is added to the
    running turn. Where it cannot, the running turn is interrupted and a new one starts with
    the message — and the button says so before it is pressed: "Send now" versus "Send now —
    interrupts". Which one applies comes from the thread's capabilities, never from the
    harness's name.
  - **Stop** stays available beside them, and stops without sending anything.
  - If the thread is waiting on an approval or a question, a message can only be queued:
    answering the card is what moves the agent on.
- Draft text and attachments persist per thread across restarts.
- An attachment in an older message whose file has since been cleaned from the target's temp
  folder shows as *no longer on the target*.

### The control row under the composer

Everything selectable about the next message. Each control appears only if the thread's
effective capabilities include it.

| Control | Shows | Rules |
| --- | --- | --- |

Opens a picker grouped by provider instance (for example *Codex*, *Codex · work*, *Claude*). | In a **draft**: every instance on the target is selectable. In a **started thread**: only models of the thread's own instance are selectable; other instances are listed but disabled with "fork to switch provider". Needs `ModelSwitch` to change mid-thread. |

corrected as soon as the target reports fresh data

what was asked for.

[effective capabilities](04-providers.md#effective-capabilities-are-computed-on-the-target),
and the row is drawn from that.

## Settings

Settings is a full-window page with its own navigation — Targets, Providers, Appearance,
Window, Keyboard, Advanced — and a control to go back to the threads. It shows no thread tree, no
agents panel, and no composer.

### Targets

- **Local** — always present; can be disabled.
- **SSH** — a list of connections. Add, edit, remove, enable, disable. See the setup flow below.
- **WSL** — shown only on Windows hosts. A master switch, **off by default**. When on, a list of
  WSL connections: each is a **distro** (picked from those installed) and an **optional user**
  (empty means the distro's default user), with its own enable switch. The same distro can be
  added again with a different user; the UI notes that this opens a second WSL session.

#### Adding an SSH connection

```
┌─ SSH connection ──────────────────────────────────────────────┐
│ Name   [ devbox            ]                                  │
│ Host   [ devbox.example.com ]   Port [ 22 ]   User [ me     ] │
│                                                               │
│ [ Setup ]                          ○ not set up               │
├───────────────────────────────────────────────────────────────┤
│ Password-less login is not available yet.                     │
│   (•) Password  [ ••••••••      ]                             │
│   ( ) Key file  [ Browse…       ]                             │
│ [ Connect ]                                                   │
├───────────────────────────────────────────────────────────────┤
│ ● Ready — set up by YAAC on 2026-11-20          [ Revoke ]    │
└───────────────────────────────────────────────────────────────┘
```

1. Fill in host, port, and user. **Setup** becomes enabled once host and port are present.
   (User defaults to the local user name.)
2. **Setup** tries to log in without a password. If that works, the connection is ready
   immediately, and it is recorded that access was already in place.
3. If it does not work, the middle section appears: enter a **password** or choose a **key
   file**, then press **Connect**.
4. **Connect** logs in with what was given. On success YAAC installs its own key for that user
   on the server, confirms it can now log in with no password, and the connection is ready.
   On failure the SSH error is shown and nothing is changed.
5. **Revoke** removes the key YAAC installed and returns the connection to "not set up". It is
   **enabled only when YAAC did the setup**. If password-less access already existed, Revoke is
   disabled, with a tooltip saying YAAC installed nothing on this server.

Around that core: a new server's host-key fingerprint is shown for confirmation on first
contact; every step reports what happened in plain words (reached the host, logged in, key
installed, key verified, daemon installed); "Import from SSH config" pre-fills the form from
hosts found there; and removing a connection that YAAC set up offers to revoke first. The
password is never saved — details in
[02 Architecture](02-architecture.md#setting-up-an-ssh-connection).

The window runs none of this itself: each step is a `hub/ssh/*` request to the hub, which runs
the SSH sessions (P45), and the "Ready — set up by YAAC on …" line comes from the hub's
record for that server (`hub/ssh/records`), so every target of the same *user@host:port*
shows the same record. A step asked for while the server's target is connected is refused
with a message saying so. If Revoke cannot reach the server, or the server no longer accepts
YAAC's key, the panel shows the exact line to remove by hand and keeps YAAC's key until the
user confirms "I removed it myself".

Three actions on a connection are kept distinct, and the page says so in one line: **Disable**
keeps the connection but stops using it; **Remove** forgets it; **Revoke** removes the key YAAC
installed on the server. Disabling a target closes its connection and greys its threads; it
does not delete anything.

### Providers (per target)

For each connected target, the provider instances found there:

- Status — ready, not installed, needs sign-in (with the command to run on the target),
  too old, unreachable — plus harness version and the **backend in use**. For Codex, whether
  `yaacd` found the daemon running or started it.
- Enable or disable an instance.
- **Add an instance:** choose the kind, give it an optional name, and set its endpoint (for
  Codex: the daemon socket path). Edit or remove later.
- "Refresh" re-probes the instance and its model list.
- A switch per instance: offer the YAAC tools to sessions of this harness started outside YAAC
  (it edits that harness's own configuration, and says so).

### Window

#### The tray

YAAC keeps an icon in the system tray (D127; Windows — no tray is built on Linux, and WSLg has
no StatusNotifier host to show one). **"Keep running in the tray when closed"** is **on by
default** (P70). With it on, the title bar's close button and Alt+F4 **hide** the window: it
leaves the taskbar, runs no egui pass and paints nothing, and wakes only when something asks
for a repaint (a hub message, a tray click) — so it costs no CPU while nothing happens. The
tray icon's **left click** (or double click) shows the window and brings it to the front; its
**right-click menu** has **Open YAAC** and **Quit**. Quit closes the window process; the hub
runs on, as it always does when the window closes. With the option off — or where there is no
tray icon — closing quits, as before.

The icon is the app icon. While some thread needs the user it carries a **small red badge**
and its tooltip reads **"YAAC · N need you"** (otherwise "YAAC"); the count is the Needs-you
list's, kept up to date while the window is hidden.

**One window per user session** (P71). Starting `yaac` while a window is open — perhaps hidden
in the tray — shows that window and exits. On Windows this is a named event in the session's
`Local\` namespace, named after the hub's pipe (so a test profile has its own): the first
window waits on it on a thread of its own; a second `yaac` signals it, lets the first take the
foreground, and exits. The demo (`--demo`, `--screenshots`) is not limited.

#### Display

A **Renderer** dropdown lists the renderers this build offers on this host (D128): on Windows
*Automatic*, *Direct3D 12*, *Vulkan*, *OpenGL (wgpu)*, *OpenGL (glow)*, *Software (WARP)*; on
Linux the same without Direct3D 12, *Software* being wgpu's CPU adapter (lavapipe or
llvmpipe). *Automatic* is OpenGL through glow, the lighter one
([02](02-architecture.md#the-renderer)). A change **applies when YAAC starts again**, and the
page says so. Under it, one line says what this window actually runs on — the renderer, the
backend and adapter wgpu ended up on, whether it draws in software, and why it fell back —
for example *"In use: Direct3D 12 (WARP, software) · fell back because Direct3D 12 failed to
start: no adapter can draw to the window"*. A fallback is never silent. A renderer that did
not finish starting last time is named, with **Try it again**.

Theme (dark, light, or follow the system), font size, send key, default grouping, whether the

## Rendering and memory

The UI must stay small and idle at zero CPU. The rules that make that true:

- **Repaint only on demand.** egui runs reactively. The I/O thread calls `request_repaint`
  when visible state changes, and coalesces a burst of stream events into one repaint per
  display frame.
- **Virtualise both lists.** The sidebar and the transcript lay out only visible rows. Item
  heights are measured once and cached until width or content changes.
- **Parse markdown once.** A completed item keeps its parsed blocks and laid-out text. While an
  item streams, only a bounded tail is re-parsed each frame — never the whole item, which would
  grow quadratically on a long answer or an unclosed code fence. When the item completes it
  gets one final, exact parse.
- **Cap what one item can cost.** A single 20 MB tool output must not become 20 MB of laid-out
  text. Large items show a bounded head and tail with "show more", fetched on demand.
- **Keep the reader's place.** Scroll position is anchored to an item and an offset within it,
  so a window resize, a font change, or content arriving above does not move what the user is
  reading.
- **Keep transcripts out of memory.** Only open threads hold items in memory, plus a small
  least-recently-used set. The sidebar holds summaries only.
- **Images at display size.** Decode to thumbnail resolution, upload to a GPU texture, drop the
  pixels. Textures are evicted least-recently-used.
- **Load syntax highlighting lazily**, per language, the first time a code block needs it.
- **Never block the UI thread — or the I/O thread.** Connection work happens on the I/O thread;
  disk writes, hashing, and image decoding happen on a small bounded worker pool; the UI reads
  snapshots.

## Accessibility

egui exposes an accessibility tree through AccessKit. The thread tree, request cards, and
composer controls carry names and states, approvals and questions are fully operable from the
keyboard, and focus moves predictably when a request arrives (it is announced; it does not
steal focus from what the user is typing).

## Keyboard

Every key the window handles is a command in **one table** (`yaac-core`'s `commands`), listed
in full — name, explanation, default key — in [the command catalogue](plan/commands.md). The
**Commander** (default Ctrl+Space, D130) searches it; **Settings → Keyboard** rebinds it (D131);
one dispatcher in the window resolves every global key through it. Three rules come first,
because they prevent expensive mistakes:

- **Approval keys act only while that card has focus.** Enter in the composer sends a message;
  it never approves something further up the page. Enter, Shift+Enter, Ctrl+Enter and Esc stay
  with the composer, and Enter and Esc with the focused card; they are listed but not
  rebindable (P76). The Commander's *Allow* and *Deny* act only on the card that had focus
  when it opened (P78).
- **A request that arrives while the user is typing does not take focus.** It is announced —
  the Needs-you count changes and a one-line notice appears above the composer — and the caret
  stays where it was.
- **Plain keys never fire in a text field.** A key without Ctrl or Alt (F2, Delete) acts only
  when focus is in the list or the thread view; the keys text editing uses (Ctrl+Delete,
  Ctrl+A, Ctrl+←…) stay with the field (P77).

**Ctrl+J** (like the Needs-you button, D117) opens the next thread that needs the user,
scrolls to the request, and focuses its card; pressing it again moves to the next one. Hover
texts and notices show each command's key as currently bound.

### The Commander

A centred overlay over a dimmed window (screens 64–66): a search field, then the list in the
shared menu style. Each row is the command's name, its one-line explanation in the secondary
colour (or, when it cannot run now, the reason), and its key on the right in a key cap. With
nothing typed the list starts with *Recent* and then every group of the catalogue; typing
filters and ranks (P80). ↑/↓ move, Enter runs, Esc closes, a click outside closes. A command
that takes an argument continues inside it: the step's name sits before the field and the list
becomes its choices (models of this harness, effort levels, modes, mute durations, orders,
grouping, theme, targets, related agents, history, settings pages); Esc or Backspace on an empty
field goes back. Dialogs that exist (fork, delete, archive, create PR, mute until a date) open
as before. The Commander draws only when a frame happens anyway — its caret does not blink — so
it costs nothing while open.

### Settings → Keyboard

Every command, grouped as in the catalogue (screen 67): name and explanation on the left, the
key cap, **Clear** and **Reset** on the right; **Reset all** at the top. Clicking the key cap
records the next chord (Esc cancels, Backspace or Delete clears). A chord another command has
is flagged under the row — "Ctrl+K is used by Search threads." — with **Replace** and
**Cancel**; a chord a local key uses is refused. Ctrl+Space carries a note about input-method
layouts (P81). Only differences from the defaults are stored, as the window preference
`keyBindings`.
