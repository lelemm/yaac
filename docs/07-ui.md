# 07 — UI

## Stack

- **Rust**, `eframe` + `egui`, GPU-accelerated. Backend (`glow` or `wgpu`) chosen by
  measurement in spike S1; see [footprint](02-architecture.md#footprint-budget).
- Markdown through a `pulldown-cmark`-based renderer (`egui_commonmark` or our own on the same
  parser), with code highlighting loaded lazily.
- No web view, no JavaScript in the host.

## Layout

```
┌────────────┬───────────────────────────────────────────────────────────┐
│ Sidebar    │ Thread header                                             │
│ threads,   ├───────────────────────────────────────────────────────┬───┤
│ a flat     │ Transcript                                            │ ◉ │ ← agents pill;
│ list       │                                                       │ ◉↓│   a card on hover;
│            ├───────────────────────────────────────────────────────┴───┤   can be docked
│            │ Composer                                                  │
│ ⚙ Settings │ Control row                                               │
└────────────┴───────────────────────────────────────────────────────────┘
```

Every screen, its exact content, and the colour tokens for dark and light mode are specified
in [design/screens.md](design/screens.md), with mockups alongside.

## Design principles

Three decisions by the owner, made on seeing the first mockups, govern everything visual:

0. **Monochrome.** There is no accent colour. Colour appears only where it carries meaning:
   needs you (a red exclamation, D113), failed, done, git changes, and — as an outline only —
   a turn that finished unseen (cornflower blue, D114).
1. **Calm before complete.** Every mark on screen must earn its place. The sidebar is a flat
   list, not a tree.
2. **Local time.** Every time shown or entered uses the time zone of the computer the window
   runs on, never the target's.
2. **No outlines.** Controls are not boxed. Things are told apart by space, then by a faint
   fill, and by a line only where two regions meet.
3. **The conversation comes first.** In a chat, what the user and the agent say to each other
   is the content; everything else is quiet.

The exact rules, colours, and every screen are in [design/screens.md](design/screens.md).

## Sidebar

**Decided: a flat list under sticky headers — not a tree.** No indentation, no chevrons, no
folder icons, no nested levels.

- **Workers** (D171). YAAC workers and harness subagents appear under **Workers** in their
  parent's agents panel while the parent is indexed. A worker whose parent is missing can
  appear in the main list. **Needs you** can open a blocked worker directly.
- **Rows (decided: two lines).** Line 1: a state mark, the title, and on the right a relative
  time. Line 2, smaller and quieter: a branch icon and the **git branch**, then — very
  compactly, with real icons and the usual git colours — how the thread's checkout differs
  from origin: files **added** (green), **modified** (soft yellow), and **deleted** (red),
  then commits not pushed and not pulled; each shown only when it is not zero. The count of direct workers,
  when there are any, sits at the **right edge of line 2**, under the time. Icons come from one small embedded icon set,
  never from Unicode symbols. A thread whose folder is not in git has a one-line row. Each state has its
  own shape, so the mark reads without a word beside it. A thread that ended its turn while its
  harness's own sub-agents still work is **waiting** (the hourglass, "Waiting" in the header and
  the agents pill) until they end, never shown idle (D188); the target reports it.
- The git line comes from the target: `yaacd` asks git once per checkout, not per thread,
  caches the answer, and refreshes it when a turn ends in that checkout and on a slow timer
  for rows that are on screen. It is never refreshed for the whole fleet at once. Counts compare
  the working tree, untracked files included, with the point where the branch left its
  upstream — so other people's pushes do not show up as your changes.
- **The PR badge** (D119, moved to line 1): at the right of the title line, **before the
  relative time** — the title ellipsizes first, so the badge and the time stay whole. An
  almost square, monochrome box: `PR#` and the number of the branch's open pull request
  (`[ PR# 33342 ]`), `+N` when the branch has more (`[ PR# 33343 +1 ]`; hovering `+N` lists the
  others, each clickable). **The badge appears only when the branch has a real pull request**
  (D143) — no placeholder. Click opens the pull request in the host's default browser;
  right-click offers **Create a new PR** and **Copy link** (and asks the target again). Hints
  (P48): dashed outline for a draft, a merge mark for merged, a struck-through number for closed,
  a small cross when checks fail, a dotted ring while they run. The docked panel's rows carry the
  same badge.
- **Create pull request…** is in the thread's right-click menu (D143) on a branch of a supported
  forge; on the default branch, or with `gh`/`az` missing or signed out, it is disabled and says
  why.
- **Create PR modal** (D120): *Into* (target branch, default the repository's default branch,
  from the remote's branches), *Title* and *Description* prefilled from the branch's commits
  and editable, **Draft**, and **Ask the agent to write it** — a message to the thread's agent
  (it costs a turn) whose reply fills title and description (P50). When the branch has unpushed
  commits or no upstream, a notice says Create will push it first; uncommitted changes are only
  warned about. An uncertain create is shown as such and never repeated.
- **Section headers.** One quiet line naming the group — the project on the left, the machine
  on the right — pinned to the top of the list while its rows scroll beneath it. Because each
  row carries its branch, sections are per project by default; the worktree level can still
  be ticked on to split them. A
  connection mark appears beside a machine only when it is *not* connected.
- Click a group header to collapse or expand its rows. The sidebar remembers collapsed
  groups. A collapsed header shows its thread count and keeps its actions available.
  Searching includes threads in collapsed groups. Right-click a group header and choose
  **New Thread** to start a draft with that group's target, project and worktree where
  the group identifies them. A temporary folder prefills the create-project dialog.
- **Grouping.** The three levels — machine, project, worktree — are still independently
  switchable ([grouping rules](05-threads.md#sidebar-grouping)); they are three checkboxes in
  one small menu on the search field. What is ticked makes up the header text. With nothing
  ticked there are no headers: just the list.
- **Ordering** (D116): an icon beside the grouping control opens a menu — **Last message**
  (default), **A → Z**, **Z → A** (by title, case-insensitive, natural order), and two
  checkboxes, both on by default: **Keep unseen finished threads at the top** and **Keep
  threads that need you at the top**. The order applies inside each group, in *Pinned*, and in
  the plain list; floated threads sit at the top of their group (needs you first, then unseen,
  each in the chosen order) and drop back once answered or seen. While the pointer is over the
  list, or a row's menu is open, a reorder is held back until the pointer leaves, so a row
  never moves away under it. A window preference, stored like the grouping.
- **There is no Needs-you section** (D116). Every thread waiting on the user — an approval, a
  question, a permission, a budget — floats to the top of its group and carries the red
  exclamation. The **Needs-you button** (D117), the same red exclamation with a count beside
  the back and forward buttons (and under them in the strip), is shown only while some thread
  needs the user; each press opens the next one, cycling through those still unresolved, most
  recent first. **Ctrl+J** does the same. Tooltip: "Next thread that needs you (N)".
- **Pinned** is the first section: threads the user pinned, from any project. Hidden when
  empty. A pinned thread is listed here instead of under its project.
- **Project sections** follow. A project shows the name the user gave it. A **temporary
  project** — a folder with discovered threads but no project yet — is shown in italics with
  a dashed mark and its folder path; right-clicking its header offers **Create project…**,
  with the folder prefilled and editable ([projects](05-threads.md#projects)).
- **Muted** is the last section, collapsed to its header. Muted threads keep working; one that
  becomes blocked is listed in its group (at the top) until answered. Muting asks for how
  long: until unmuted, for a number of minutes, hours, or days, or until a chosen date and
  time — a date field with a calendar button that opens the calendar as a dropdown, always six
  week rows so it never changes size (D112); a timed mute ends by itself.
- **Archived** comes after *Muted*, also collapsed to its header — "Archived · 12" — and lists
  archived threads when opened; Unarchive is in each row's menu. It replaces the earlier "Show
  archived" switch. **Archiving a thread removes its pin and its mute**: an archived thread is
  only ever in *Archived*.
- **Right-click a row** for the thread menu (D109): **Copy thread ID, Rename** — separator —
  **Fork, Pin / Unpin, Mute… / Unmute, Archive…** (Unarchive on an archived row) — separator —
  **Delete…** in the destructive colour; on a thread outside any project, **Dismiss**, which
  just hides it ([details](05-threads.md#dismissing-a-discovered-thread)). Rename, Archive and
  Delete's harness option follow the thread's capabilities. While the menu is open the row
  keeps its hover colour (D108). **Archive…** asks for confirmation in a modal (D111).
  **Delete…** opens "Delete *title*?" with **"Also delete the session from *harness*"**,
  checked by default and shown only under the `threadDelete` capability (D110); YAAC's own
  record and journal always go. The request carries an operation id; a lost answer is shown
  as an unknown outcome and never re-sent. Once deleted, the thread leaves the list, the
  history, and the view preferences.
- **Several threads at once** (D138, P95–P99). **Ctrl+click** adds a row to a selection (or
  takes it out), **Shift+click** selects every row from the anchor to it in the order shown,
  across groups, and a plain click opens a thread and clears the selection. With focus in the
  list, **Esc** clears it, **Ctrl+A** selects every listed row and **Shift+↑ / ↓** extend it. The
  selection is separate from the open thread and drawn apart from it: the selection tint with a
  bar in the primary text colour at the row's left edge. Only listed rows stay selected — one
  filtered out, collapsed, archived or removed leaves the selection; a reorder keeps it.
  Right-clicking a selected row keeps the selection. For two or more rows its menu offers
  **Archive selected (N)…**, **Mute selected (N)…**, **Unmute selected** when any is muted, **Clear selection** — and
  a bar under the list reads "3 selected · Archive · Mute ×". **Each group header and Pinned**
  has **Archive all (N)…** and **Mute all…** for the rows it lists now (right-click it, or the
  dots shown while the pointer is on it); a temporary project's header keeps **Create
  project…** and **Dismiss all** above them. **Archive** asks once for all — "Archive 3
  threads?" — and says what it skips and why ("3 of 5 can be archived; 2 are running"):
  threads whose harness lacks `threadArchive`, on a machine that is not connected, running,
  waiting on another agent or on the user, in use elsewhere, or already archived. Each thread
  gets its own `thread/archive` and operation id, never re-sent; when the answers are in, any
  that failed or whose outcome is unknown are reported once in the bar ("2 could not be
  archived: … · uncertain: …", the reasons on hover). **Mute** opens the Mute dialog once
  ("Mute 3 threads") and applies the choice to all in one `hub/view/setMany`; Unmute selected
  is one too. The Commander has *Archive selected…*, *Mute selected…* and *Clear selection*.
- **Moving a thread to another project or worktree** (D144, P100–P105) — **on its own
  machine**; the machine never changes. Three ways in: **Move…** in a row's menu (after
  Fork), **Move selected (N)…** in the selection's menu, and **dragging** rows. The **Move
  dialog** shows the machine, a **Project** dropdown (that machine's projects) and an optional
  **Worktree** dropdown (the project's own checkout and the others YAAC knows there), and one
  sentence saying what happens: "The agent will work in <path> from its next turn" when the
  thread's harness has `threadMoveWorkingDirectory`, otherwise "Only where YAAC lists it
  changes; the agent keeps working in <old path>". It is disabled with the reason when the
  thread is in use elsewhere, archived (no Move at all), or its machine is not connected.
  **Dragging** a row — or the selection, when the row is in one of two or more — onto another
  group (its header or its rows) moves it to that group's project, and checkout when grouping
  by worktree; it works while the grouping has a project or worktree level. The group under
  the pointer is outlined in the focus colour and a card by the pointer says "Move to api";
  over another machine's group, a temporary project, or a group of several projects, the
  cursor is not-allowed and the card says why ("A thread cannot move to another machine"). Esc
  cancels. Rows do not reorder while dragging (D116). A drop that changes some agent's folder
  opens the Move dialog to confirm; otherwise the rows move at once and the bar under the list
  reads "Moved 2 threads to api · Undo". A running thread may move: the change applies from its
  next turn. Each thread gets its own `thread/move` and operation id, never re-sent; a refusal
  puts the row back and is reported in the bar. The transcript records each move ("Moved to api
  · working directory now /home/dev/api" or "Moved to api in YAAC · working directory
  unchanged"). The Commander has *Move to project…* (a step over the machine's projects and
  their worktrees, then the dialog) and *Move selected…*.
- **A finished turn nobody looked at** (D114): when a thread's (or a subagent's) turn ends and
  no window shows that thread, the hub marks it *unseen* — a view preference beside pin and
  mute, so it survives a restart and every window agrees. The row gets a cornflower rounded
  outline (sidebar, docked panel), a ring around its icon (pill, strip). Opening the thread
  clears it. Needs you, paused, failed and running take precedence: while one of those marks
  shows, the outline is not drawn. It is not part of *Needs you*.
- **A narrow row keeps every mark** (D115): the title — and the branch on line 2 — is
  ellipsised; the state mark, harness logo, git counts and ahead / behind stay. Archived threads
  leave the list; a "Show archived" switch in the same menu as the grouping brings them back,
  and search always finds them.
- **The selected row is always the open thread**, drawn as a tint so everything on it stays
  readable. Rows chosen for a bulk action (above) are a separate selection with its own look.
- **Needing the user outranks every other state.** A thread with a pending request shows
  *needs you*, not *running*. That is the thread's own state; its parents carry no mark for it.
- A machine whose daemon is on an older version carries a warning mark; its tooltip says
  *"Running an older YAAC daemon — it will be updated when idle"*, with **Update now**
  ([09 Compatibility](09-compatibility.md#upgrading-a-daemon-without-interrupting-it)). The
  thread banner says the same; **Update now** asks first only when turns there would be
  interrupted, with how many, and the banner then reads *"Updating yaacd on devbox…"* until the
  newer build serves ([how the hub does it](02-architecture.md#one-serving-daemon-per-user)).
  While the daemon restarts, the sidebar and composer show "Updating YAAC daemon…".
- **A WSL distro that is down** raises a notification with one action, **Start it**. Its
  threads stay listed but are disabled — readable, with the composer replaced by "Ubuntu is not
  running" and a **Start it** action — and become responsive again once the distro is up. YAAC never starts a
  stopped distro on its own.
- An offline machine's threads remain visible from cache, with "offline" beside the machine.
- Only recent threads are listed: discovery is capped by age and number
  ([details](05-threads.md#discovery-is-capped-by-age-and-by-number)). A project section ends
  with "Show older" when the target has more, and search offers "Search older threads on
  *devbox*".
- **Back and forward** buttons beside the title step through the places the user has been —
  threads, settings, drafts — like a browser, each remembering its scroll position. Holding or right-clicking a button
  lists the places in that direction, to jump several steps at once. The
  mouse's back and forward buttons and Alt+← / Alt+→ do the same.
- With a live hub, both renderers search across attached targets by fuzzy title or thread ID
  and can load more results. Without an attached hub, search filters the local index by title
  and preview.
- A row's right-click menu has **Copy thread ID**, so a thread can be named to another agent: "tell
  thread 0198a1c4 on devbox when you finish".
- **New** at the top opens a draft with no target, project or checkout selected (D107). Pick a
  project under its machine, then choose a worktree if needed. Drafts stay out of the sidebar.
  The welcome screen recommends a connected machine with a ready provider, preferring this
  computer, and lists its providers.
- The footer holds Settings and a quiet **hub status** (D106): a connection icon in a muted
  colour — crossed out while the hub cannot be reached — then the targets as counts only: an
  up arrow with the number connected and a down arrow with the number not connected (the
  down count is hidden when it is zero).
- **The sidebar is resizable** by dragging its edge, and **collapses into a vertical strip**
  (button, Ctrl+B, or dragging past its minimum): the YAAC mark, a + button, the history
  buttons side by side, each project's name written vertically (Pinned as a pin icon) with one
  harness logo per thread carrying its state as a corner badge (the red needs-you exclamation
  when it needs the user, a cornflower ring when its turn ended unseen), a hairline between projects, and Settings (D103). Hovering an icon shows the full row in a floating card; the wheel scrolls the
  strip. Below 1,000 logical points the window uses the strip temporarily and restores the
  saved sidebar width on widening.

With the window closed, the hub raises a desktop notification for anything that needs the user;
it opens the exact request.

### The rate-limit panel

**Decided (D161); Proposed (P234–P237).** Docked at the bottom of the sidebar, just above the
footer: the plan rate limits of every account any target uses, and when they reset — one group
per account, **deduplicated across targets by the account** (the same Claude sign-in on WSL and
on devbox is one group). Hidden when no account reports limits. Screens 110–112.

- A group is the provider's **logo** (D97), then one **segmented bar** per window — five
  segments of 20%, used ones filled, the partly used one dimmer, the rest a faint track — with
  **"55% · 2d"** beside it: the share used and the time until the window resets, in whole
  minutes, hours, or days rounded down ("53m", "4h", "2d"). The account-wide windows are shown,
  shortest first (5h above weekly); a scoped one (a model's own weekly limit) only once it is
  at 90% or more. A window past its reset reads "0%" until the harness reports again.
- **Coloured by the provider**, an exception to the monochrome rule like the logos (D98), and
  like them looked up from the kind as data: Claude in its brand orange `#D97757`, Codex in
  blue `#3478F6` (3.8:1 on the light sidebar, 4.1:1 on the dark one). At **90% or more** the
  text is the failed colour. A group whose account no connected target reports is drawn dimmer.
- Groups sit side by side and are centered horizontally and vertically on each row, wrapping
  when the sidebar is too narrow. They are ordered by provider, then plan.
- **Tooltip** per group: the plan and the sign-in's email, each window's exact share and reset
  in local time (D91), which targets use the account, and, when stale, that the values are the
  last known and when they were reported.
- **In the collapsed strip** each account shows its logo above thin bars for the same windows,
  above Settings. Hover for the account details.
- **It never repaints on its own** except when the countdown's text would change: one repaint
  is scheduled for then, never sooner than a minute. Fresh values come from the harnesses'
  own reports; while the panel is drawn the window asks for a refresh at most every five
  minutes (the hub and `yaacd` hold their own five minutes too), as the pull-request badges do
  (P49).

Both renderers use the bundled Ubuntu Sans Nerd Font Propo for interface text and chat.
Code and command output use CaskaydiaCove Nerd Font Mono. Both families include Powerline and Nerd Font glyphs.
The composer uses a base text size of 14.5 in both renderers. WPF uses grayscale antialiasing
for the composer's text.

## Thread view

- Open at the newest page. Scrolling towards either edge fetches the adjacent page while
  keeping the visible message anchored. A history page is shown after its boundary turn
  is complete, including when a long turn takes several wire pages. The window trims whole
  turns so an older reply appears with its **Worked** group already formed. Both renderers
  virtualise the rows inside the history window. WPF measures visible rows and an offscreen buffer at the current
  chat width, with their current expanded or collapsed state. It adjusts the pixel offset
  before drawing so measuring newly encountered rows or loading a page keeps the top
  visible message in place. **Latest messages** returns to the live end. If a paging
  anchor is no longer available, the transcript refreshes from the newest page.
- Error notices can be dismissed in place. Thread errors appear beside that thread's composer.
  Window-wide errors appear at the bottom of the window.
- **Decided: the conversation comes first.** Only the user's messages and the agent's prose
  are full size. Everything else is *activity* — reasoning, tool calls, messages to and from
  other agents, workers being started, waiting — and is shown **collapsed by default as one
  muted line**: `Ran cargo test — passed`, `→ CI integration · delivered`,
  `← billing-service · Migration merged. 14 tests…`.
  - Consecutive activity lines sit tight together as one quiet run; a long run folds into a
    single summary line that expands to the lines.
  - A collapsed tool call shows a one-line command preview, including when the command spans
    multiple lines. Clicking the line expands its detail in place with the full command and
    output. Agent message activity can expand to show the whole message and its receipt.
  - A failed shell command breaks the activity run. It gets its own expandable error line
    between two independent runs and stays visible when the turn's work is folded. Both
    renderers use the same split, so you can open the failed command's output directly.
    A red cross marks the failure. The row uses the same text color as a successful command.
  - A failed agent call keeps the tool name and failure mark in the row. Open it to read the
    wrapped reason, or open **Raw call** for the original input and output.
  - Reasoning reads "Thinking…" while under way and "Thought for 4s" when done. If it has text,
    the row opens by default and renders its body like an assistant message. The header still
    collapses the row, and the surrounding activity and turn folds apply as usual (D179).
    **Reasoning with nothing to read is not a line** (D148, P170): Codex's hidden
    reasoning (an empty summary, the reasoning itself encrypted) between almost every command,
    or an empty thinking block, is shown only when it took at least 2 s — "Thought for 6s",
    which explains a pause and has no disclosure — and never while under way, so no
    "Thought for 0s" and no line that flickers in and out. The rule is about content, the same
    for every harness (screen 84).
  - What needs the user is never collapsed: approvals, questions, the permission prompt, and
    the budget notice are the only cards in a transcript.
  - In a thread an agent started, the message that set its task is shown in full where a user
    message would be, labelled with who sent it.
- **A user message shows what the user wrote, pasted and ran — never a harness's markup**
  (D141, P121). `yaacd` splits it into parts with a role ([03](03-protocol.md#input-parts)):
  - typed text keeps single line breaks and renders Markdown formatting (D157);
  - a paste is a quiet inset block, **"Pasted text · N lines"** with a chevron, collapsed;
    opened, the text as pasted — plain text with its own copy button, or code when the paste
    is itself a fenced block;
  - a command is a compact monochrome chip: `/model opus`, `!ls`;
  - what the harness added for the model (system reminders, environment, AGENTS.md, IDE
    selection, hook and command output, YAAC's handoff note) is not in the bubble: a small
    **"Context"** disclosure under it opens each part under its label, in secondary text. A
    message that is only context is that one quiet line, without a bubble.
  - **Copy message** copies the typed text, the pastes and the commands, without context.
- Messages that did not come from the user — a subagent's hand-back, another session's
  message, a background task finishing, a turn the mesh started read back from the harness —
  are notice lines with their meaning ("Subagent schema-check reported back", the task's
  summary), expanding to their plain text; never the envelope's tags (P122).
- **A stopped turn says so in a quiet line, not a user bubble** (D167, P276–P277). Claude
  Code writes `[Request interrupted by user]` (or `… for tool use`) as a user-role message when
  a turn is stopped; YAAC shows it as an activity line with a small stop mark — **"Interrupted"**,
  or **"Interrupted during a tool call"** — live and in history, inside the turn it stopped. A
  Codex message that is only `<turn_aborted>` reads the same. A finished turn's fold already
  says *· interrupted* for both harnesses; the line is what it shows when opened.
- Every one-line row flattens its text: a line break or control character is a space, never a
  missing glyph (P123). HTML in markdown is shown as the text it is.
- Agent text streams in as markdown. Code blocks have a copy button. File changes are diffs:
  a collapsed line with `+12 −3` that expands to a unified diff, and one summary line at the
  end of a turn that changed files.
- **All text can be selected and copied**, including one selection across several items.
- Pending `request` items render inline as an approval or question card and also raise the
  thread's attention state in the sidebar. An approval card shows the decisions the harness
  actually offers, not a fixed Allow/Deny pair. A question card shows each question with its
  options, multi-select where allowed, and a free-text answer where allowed; a secret answer is
  masked. Cards also show what happened next: *submitted*, then *confirmed — answered by
  you* once the agent acknowledges it; and the quieter outcomes *resolved elsewhere*, *expired*,
  and *outcome unknown*, which offers "Check latest status" and never a resend
  ([request states](03-protocol.md#request-states)). A secret answer is masked while typed and
  in every summary afterwards.
- **Back to the newest message** (D142). Scrolled up, the thread shows a button above the composer — "3 new messages (Ctrl+End)" when messages arrived since the view left the bottom, otherwise "Jump to bottom (Ctrl+End)". It goes away once the view is at the end again.
- **The user's messages stand out** (D155, P214). The bubble has its own fill (`user_bg`),
  clearly stronger than the faint fill, and sits at the **right** of the column: as wide as a
  short message, at most 80% of the column (a message with code, a table, a list, a paste or
  files takes the 80%). The task that started a spawned thread stays at the left on the faint
  fill, labelled *From* — it did not come from the user.
- **A message's time shows while it is hovered** (D154, P213), small and secondary, in the
  line kept free under every message so nothing moves: "22:15" today, "25 Oct, 22:15" this
  year, "25 Oct 2025, 22:15" before, in the host's time zone (D91). The user's message shows
  when it was sent, at the right under the bubble; the agent's when it finished, at the left.
- **A thread in use elsewhere is read-only.** The transcript keeps updating, a banner says
  where it is in use ("in use in another program", "in use on *laptop*"), the composer is
  disabled, and request cards are shown without their buttons. Fork stays available
  ([05 Threads](05-threads.md#in-use-elsewhere)). For a program on the target whose harness
  allows it (`threadTakeOver`), the banner's primary button is **Take over** (D140), with
  **Fork to continue here** beside it: one click, a tooltip "Continue here. The other program
  is not stopped and will not see what you send from now on.", "Taking over…" while in flight,
  then the banner goes and the composer unlocks; a failure's reason shows under the sentence and
  is never retried. When the holder will not let go (a Claude Code background session, a turn
  running there) **Take over** is unavailable and the reason is shown instead. Also in the
  thread menu after **Fork**, and in the Commander (P112).
- A forked thread shows its inherited history above a divider, read-only.
- Sticks to the bottom while streaming unless the user has scrolled up. **A streaming message
  never moves the view backwards** (D152): each frame shows the end of its own final layout, and
  the content only grows. A block keeps its last measured height while its text changes
  (keyed by which block it is, not by what it says, P200) and is measured again when drawn;
  when a drawn block's height changes, egui lays the frame out again before showing it
  (`request_discard`), so no frame shows a guessed or stale height. At the bottom, each pass
  starts at the end of its own layout.
- **Identical wheel steps move the transcript by the same amount; visible content never jumps
  when other messages are measured** (D163). Scrolled up, each pass remembers the block reaching
  into the top of the view and the view's offset from it; the next pass places the view from
  that block's new position (scroll anchoring, as browsers do, P250), so a block above it that
  is measured for the first time, folds or opens, or rewraps at a new width moves the offset,
  not what is on screen. A wheel notch is then one notch of content everywhere, up from the
  bottom as down from the top, and egui's smoothing of the notch carries on undisturbed. A
  block not drawn yet is placed at a guess from what it holds at the column's width — its
  lines, code lines and the space between its paragraphs, a user message at its bubble's
  share — instead of a flat height (P251), so the content height and the scroll bar are close
  to true before the blocks are measured. At the bottom the view sticks to the end (D152)
  instead; a jump (to the bottom, a timeline dash, Back and Forward) sets the view and the
  anchor follows from there.
- Header shows the state mark and title (editable under `ThreadRename`), origin, project, and
  worktree, and — for a thread with relatives — a line of links: *spawned by*, *forked from*,
  or the full ancestry for a worker several levels down.

### The timeline

**Decided (D153):** a narrow column at the transcript's left edge with **one short muted dash
per prompt** — each message the user typed, and the task that started a spawned thread (P210)
— evenly spaced and centred. The dashes of the prompts **in view are longer and in the primary
text colour**, so the column is a map of where the view is in the conversation.

- The timeline lists the whole chat from compact prompt metadata. **Hover** a dash to see
  its prompt's first line and time. **Click** to scroll to that prompt, fetching its page
  directly if its message is outside the current history window.
- **Dense threads** pack the dashes closer, down to 3 points apart; past that, neighbouring
  prompts share a dash (each dash an equal share, its card adds "and N more"). Clicking a
  shared dash opens a list so any of its prompts can be selected (P211).
- Hidden while the thread has fewer than two prompts.
- The column is drawn with the transcript and never animates: the highlight changes only when
  the view scrolls, which repaints anyway.
- **Go to previous / next message** (Alt+PageUp / Alt+PageDown, rebindable; in the Commander)
  scrolls to the prompt before or after the one in view (P212).

### A finished turn folds

**Decided (D156):** while the agent works, its reasoning, tool calls, diffs and interim
messages stay as they are. **When the turn ends** — finished, interrupted or failed —
everything between the prompt and the agent's **final message** folds into one quiet line,
and the final message is shown in full under it:

- `Worked for 26s ›` — the turn's wall-clock time ("26s", "4m 12s", "1h 3m");
  `Worked for 26s · interrupted ›`; `Worked for 26s · failed ›` in the failed colour, with the
  error under it.
- **Clicking the line opens the turn's work** in place (the chevron turns down); clicking again
  folds it. Which turns are open is window state, like the other expansions. **Expand all tool
  lines** opens every turn, **Collapse all** folds them again; opening a turn's "show all"
  files, or navigating to an item inside it, opens it too.
- **Never hidden:** an approval or a question still waiting (a turn waiting on the user is not
  finished), the budget notice, and the turn's **Changed N files · show all** line, which stays
  under the final message.
- A turn with nothing to fold has no line; a turn another agent's message started (no prompt of
  its own) is not folded, so that message stays in view.
- Older history loads folded the same way. A folded turn's hidden items are not part of a
  selection or a copy until opened.
- When a turn counts as finished, and how its outcome and duration are read: P215, P216.

## Agents in the thread view

**Decided:** the thread view shows the sub-threads of the open agent in a side panel, and the
chat shows messages between agents — naming who they went to and who they came from.

### The agents panel

**Decided: three states, smallest first.** It answers "who is this agent working with, and how
is each of them doing?" — and by default it does so in 44 pixels. It exists only for a thread
that has a parent, workers, or contacts.

A small arrow beside an icon while data is moving: up for sending to that agent, down for receiving from it. The red exclamation on an agent that is blocked on the user, a cornflower ring on one whose turn ended unseen. Finished agents dimmed. |

first (P290). The pill draws at most **7 icons** (fewer in a short window, P291). When more are

(P295). Screens
130–133.

A harness's own sub-agent ([D151](05-threads.md#harness-sub-agents)) is a Worker like a YAAC
worker, beside it. Its row says what it is in place of the provider — "Claude subagent ·
Explore" (the card's second line, the docked row's provider line) — and a mesh worker's docked

there whenever its parent is (`AppState::may_answer`), it is listed in Needs you, and its row
in the parent's pill carries the needs-you mark.

In every state an icon or row opens that thread. The docked panel is drawn in the same muted
style as the rest: no boxes, no rules, names as links. Whether it is docked is remembered. Docked, it is **resizable** like the sidebar (D105): its
hairline is a drag handle, between 240 and 520 points, and the width is remembered. Its
displayed width is capped at 40% of the workspace. Below 1,000 logical points it temporarily
folds to the pill and docks again when the workspace widens.

The arrows are the one piece of motion in the interface, and they are tied to something real:
an arrow is shown only while a message or a result is actually in flight, and it repaints only
then — an idle fleet still costs no CPU.

When an orchestration's [budget](10-agent-mesh.md#every-orchestration-has-a-root-and-a-budget)
runs out, the root thread shows a notice — nothing was cancelled, how many messages are
waiting — with one primary action, **Continue**. The budget never hides what the thread does
(D164): while its own turn runs it keeps its spinner and "Running" tag, with a quiet
"Agent budget reached · Continue" beside the tag — also at the top of the agents card, under
the budget in the docked panel, and as a small ❚❚ at the top of the pill. Only while the
thread is idle and a turn an agent would start is held back does it show ❚❚ and **Paused ·
budget reached** and count as needing the user (it floats to the top of its group and the
Needs-you button includes it); then Enter answers the notice's **Continue**.

## Composer

A thread’s **Files** side pane can contribute a code selection to its composer. Select text in a File or Diff tab and choose **Add to composer** or press Ctrl+Shift+A. The reference appears at the saved caret, with a removable chip showing the file name and line range. Sending or queuing expands the reference in place into the relative path, line range and fenced selection. [Files and diffs](12-files.md)

- In egui and WPF, type `@` at the start of a word to search for files under the current
  working directory on the target. This also works in a new draft once it has a working
  directory. Type to narrow the results, use ↑ and ↓ to choose, and press Enter or Tab to
  insert the absolute path. Clicking a result also inserts it. Esc closes the picker.
  The harness receives its native quoted file mention when it offers that capability. Other
  providers receive the absolute path in a code span, including any spaces. Text on either
  side of the active reference stays in the draft.
- Submit `/compact` by itself to compact the context of an idle conversation that offers
  **Compact**. The composer says **Compacting context…** while the harness runs it and the
  transcript shows **Context compacted** when the harness confirms it. Earlier messages
  stay visible. A refusal leaves the command in the draft. An uncertain result is shown
  and is never retried automatically.

- Drag the composer's right edge to resize the centered composer and transcript together.
  The window uses the same width across chats, including drafts. The starting width is 860,
  the minimum is 360 when space allows, and the maximum is 95% of the chat viewport. The
  transcript rows use the full column width throughout that range.
- **A narrow column stacks the buttons.** Below 500 points (beside the side pane, for
  example) the composer's buttons — Queue, Send now, Stop, Send, the attachment button — move
  to their own row under the text field instead of squeezing it; wider, they sit beside it.
  Both renderers do the same.
- **Multi-line text input (decided).** The empty composer is **three lines tall in WPF** and
  two lines tall in egui. **Shift+Enter** starts a new line and Enter sends. As
  the text grows the composer grows with it, **up to five lines**; beyond that its height stays
  put and the text scrolls inside it, with a scrollbar. Wrapped lines count as lines. It
  shrinks back as text is removed and returns to its default height after sending. The transcript
  keeps its place while the composer changes height.
- **Markdown in the composer (decided): styled as you type.** Emphasis, headings, inline code,
  and fenced code blocks are visibly formatted in place, and the markdown characters stay
  visible and editable. It is one plain-text editing surface, so the caret, selection, undo,
  and input-method composition behave exactly like a normal text box. Formatting work is
  bounded, so pasting a very large text does not stall typing. Typing never restyles text it did not change: a
  keystroke at the end leaves every line above it styled as it was (P317).
- **Skills (Proposed, D172).** Typing `/` as the first character opens a picker of the thread's
  skills above the composer; `$` at the start of a word opens it where the provider names skills
  inline. It filters as you type (names that start with it, then names that contain it, then
  descriptions), **↑ ↓** move, **Enter** or **Tab** (or a click) insert `/name ` or `$name `,
  **Esc** closes it for that trigger and keeps the text. While it lists rows Enter picks instead
  of sending. Paths (`/home/me`), money (`$5`) and a `$` in the middle of a sentence never open
  it. A trigger the provider does not support leaves the text alone and shows a tooltip naming
  the provider. The picker says "Loading skills…", or why the list failed with **Retry**. It is
  the same in the egui and WPF windows ([04](04-providers.md#skills-are-a-capability)).
- **Enter and input methods.** While an input method is composing (Japanese, Chinese, Korean,
  dead keys), Enter confirms the composition and never sends the message.
- **Paste and drop** files and images; each becomes a chip with upload progress
  ([06 Attachments](06-attachments.md)). Pasted text replaces the selection and leaves the
  caret right after it, in both windows; the window's later copy of the draft does not move it
  back.
- **A sent message shows at once** (D165, P270–P275). On Send the composer clears and the
  message — its text and attachment chips — is at the end of the transcript as the user's
  bubble, with a quiet **"Sending…"** in the line under it, in the same frame; it does not wait
  for the round trip to the target and the harness. When the message's own item arrives
  (carrying the send's operation id) it takes the echo's place: same position, same height,
  never shown twice. A message that went to the queue instead leaves the transcript; the
  queue shows it.
  - **Not sent** (refused, or the target was unreachable): the bubble stays with the error in
    the failed colour and **Edit** — text and attachments back in the composer, the bubble gone
    — and **Retry**, which sends it again under a new operation id. Nothing is sent again
    unless the user clicks Retry.
  - **Outcome unknown** (contact lost before the answer): the bubble says *"YAAC lost contact
    while sending this. It may or may not have arrived; it will not be sent again."* with
    **Edit** and **Dismiss**, never Retry. If the message did arrive, its item replaces the
    bubble as usual.
- **While a turn runs, a message can be queued or sent now** (decided — the same choice an
  agent has through the mesh tools):
  - **Enter queues it.** The message waits and is delivered when the running turn ends. It is
    held by the daemon, not by the window, so it is delivered even if the window is closed.
    Queued messages sit in a small strip above the composer, in order. Each has **Send now**,
    which stops it waiting and sends it at once (steering or interrupting, exactly like
    Ctrl+Enter), and can be edited or cancelled, until it is delivered.
  - **Ctrl+Enter sends it now.** Where the harness can steer, the message is added to the
    running turn. Where it cannot, the running turn is interrupted and a new one starts with
    the message — and the button says so before it is pressed: "Send now" versus "Send now —
    interrupts". Which one applies comes from the thread's capabilities, never from the
    harness's name.
  - **Stop** stays available beside them, and stops without sending anything.
  - If the thread is waiting on an approval or a question, a message can only be queued:
    answering the card is what moves the agent on.
  - **What it looks like (D166, P280–P285).** While a turn runs the text box stays usable and
    the buttons sit beside it as when idle, so the composer keeps its height: the attachment
    button, **Queue ↵** (the primary), **Send now** (or "Send now — interrupts") and **Stop**
    (Esc); Send now and Stop name their keys in their tooltips. With
    the Ctrl+Enter send key, Ctrl+Enter queues and Ctrl+Shift+Enter sends now. While an
    approval or question waits, only Queue shows and the hint says the message will wait.
    The strip reads "Queued · 2 · sent when the turn ends", one row per message: its first
    line, Send now, **Edit** (opens it in the composer: **Save ↵** or **Cancel edit**) and ✕.
    A delivered message leaves the strip and appears in the transcript. A lost answer is
    said, never re-sent. Screen 120.
- Draft text and attachments persist per thread across restarts.
- An attachment in an older message whose file has since been cleaned from the target's temp
  folder shows as *no longer on the target*.

### Running commands

The collapsible **Running commands** strip sits above the composer in egui and WPF. It
shows shell processes reported running for this thread and its descendant workers on connected
targets. Agents themselves appear in Related agents. Each command row shows who ran it,
the target, and the time since the process was
first observed. The strip survives turn and worker completion while the process remains
live. Command text and log output use smaller, muted text. The window remembers the
disclosure state per thread while it is open. In egui, the heading uses the same drawn

**Logs** opens a live output tail when the harness exposes it. The panel keeps the last

**Started background command** with the shell input after a confirmed background launch.

## Settings

Settings is a full-window page with its own navigation — Targets, Providers, Appearance,
Window, Keyboard, Advanced, About — and a control to go back to the threads. **About** shows this
YAAC's version and build (`Build 1001`, or *Development build*), links to the releases and the
source, and the **Components** list: this window, the hub, each target's `yaacd`, and the latest
release, each with its build and whether it needs updating (D135, D136). It shows no thread tree, no
agents panel, and no composer.

### Targets

- **Local** — always present; can be disabled.
- **SSH** — a list of connections. Add, edit, remove, enable, disable. See the setup flow below.
- **WSL** — shown only on Windows hosts. A master switch, **off by default**. When on, a list of
  WSL connections: each is a **distro** (picked from those installed) and an **optional user**
  (empty means the distro's default user), with its own enable switch. The same distro can be
  added again with a different user; the UI notes that this opens a second WSL session.

  The distro is a **dropdown of the installed distros**, which the window asks of the hub
  (`hub/wsl/distros`; the window never runs `wsl.exe`, and listing starts no distro) when the
  Targets page opens and again from the small refresh button beside it; while it loads it
  says "Loading…". Each entry shows the name, "· default" on Windows' default distro, whether
  it is running, and "already added" when a WSL connection to it exists — it stays selectable,
  since another user is allowed. The **default distro is selected** at first, **unless a WSL
  connection to it already exists** (for any user): then nothing is selected ("Choose a
  distro") so the user picks another. A refresh keeps the user's choice while that distro is
  still installed. **Add** stays unavailable until a distro is chosen. If the hub cannot list
  the distros (no WSL, or `wsl.exe` fails), the row shows the reason and the distro is typed
  instead, so the user is never stuck.

#### Adding an SSH connection

```
┌─ SSH connection ──────────────────────────────────────────────┐
│ Name   [ devbox            ]                                  │
│ Host   [ devbox.example.com ]   Port [ 22 ]   User [ me     ] │
│                                                               │
│ [ Setup ]                          ○ not set up               │
├───────────────────────────────────────────────────────────────┤
│ Password-less login is not available yet.                     │
│   (•) Password  [ ••••••••      ]                             │
│   ( ) Key file  [ Browse…       ]                             │
│ [ Connect ]                                                   │
├───────────────────────────────────────────────────────────────┤
│ ● Ready — set up by YAAC on 2026-11-20          [ Revoke ]    │
└───────────────────────────────────────────────────────────────┘
```

1. Fill in host, port, and user. **Setup** becomes enabled once host and port are present.
   (User defaults to the local user name.)
2. **Setup** tries to log in without a password. If that works, the connection is ready
   immediately, and it is recorded that access was already in place.
3. If it does not work, the middle section appears: enter a **password** or choose a **key
   file**, then press **Connect**.
4. **Connect** logs in with what was given. On success YAAC installs its own key for that user
   on the server, confirms it can now log in with no password, and the connection is ready.
   On failure the SSH error is shown and nothing is changed.
5. **Revoke** removes the key YAAC installed and returns the connection to "not set up". It is
   **enabled only when YAAC did the setup**. If password-less access already existed, Revoke is
   disabled, with a tooltip saying YAAC installed nothing on this server.

Around that core: a new server's host-key fingerprint is shown for confirmation on first
contact; every step reports what happened in plain words (reached the host, logged in, key
installed, key verified, daemon installed); "Import from SSH config" pre-fills the form from
hosts found there; and removing a connection that YAAC set up offers to revoke first. The
password is never saved — details in
[02 Architecture](02-architecture.md#setting-up-an-ssh-connection).

The window runs none of this itself: each step is a `hub/ssh/*` request to the hub, which runs
the SSH sessions (P45), and the "Ready — set up by YAAC on …" line comes from the hub's
record for that server (`hub/ssh/records`), so every target of the same *user@host:port*
shows the same record. A step asked for while the server's target is connected is refused
with a message saying so. If Revoke cannot reach the server, or the server no longer accepts
YAAC's key, the panel shows the exact line to remove by hand and keeps YAAC's key until the
user confirms "I removed it myself".

Three actions on a connection are kept distinct, and the page says so in one line: **Disable**
keeps the connection but stops using it; **Remove** forgets it; **Revoke** removes the key YAAC
installed on the server. Disabling a target closes its connection and greys its threads; it
does not delete anything.

### Providers (per target)

**Automatic session discovery** pauses or resumes harness session scans on the selected target.
The setting is stored there and applies to all of its provider instances.

For each connected target, the provider instances found there:

- Status — ready, not installed, needs sign-in (with the command to run on the target),
  too old, unreachable — plus harness version and the **backend in use**. For Codex, whether
  `yaacd` found the daemon running or started it.
- Enable or disable an instance.
- **Add an instance:** choose the kind, give it an optional name, and set its endpoint (for
  Codex: the daemon socket path) and, for a kind whose instances report `configurableHome`,
  its harness home. A second instance of a kind needs a name, its own socket, or its own
  harness home. Edit or remove later.
- **Harness home** (P300), shown only for an instance that reports `configurableHome`,
  including the implicit default instances: a line under the instance, "Home · <folder>"
  (with "(default)" when nothing is set), and **Change**. Change opens an inline field whose
  placeholder is the folder in use ("Default · /home/me/.codex"), with **Save**, **Use
  default** (when a home is set) and **Cancel**; empty means the harness default. When the
  target answers that the new folder is another store, nothing has changed yet and the row
  asks: "<new> is another store than <current>. This instance's threads stay with <current>
  and show as unavailable until the home is changed back. Change the home?" with **Change
  home** and **Keep current**. Only **Change home** sends it again, as a new operation. Both
  renderers show the same rows: egui inline, WPF as Settings rows (a "Harness home" row with
  Change, an inline edit row, and an "Another store" row with the two actions).
- A thread whose instance now leads to another store (P10, P300) is read-only: a warning
  banner under its header gives the target's reason, and the composer is replaced by that
  reason, in both renderers.
- **Refresh** next to the target picker re-probes all providers and models on that target,
  even when the instance list is empty. **Refresh** on an instance row re-probes just that instance.
- A switch per instance: offer the YAAC tools to sessions of this harness started outside YAAC
  (it edits that harness's own configuration, and says so).
- A switch per instance, **"Trust folders YAAC works in"** (D147), on by default, shown only for
  an instance that reports `folderTrust`: when YAAC starts a thread in a project's folder, it
  marks that folder trusted in the harness, so the harness's own interface does not ask about
  it later ([05](05-threads.md#folder-trust)). It is stored in that instance's configuration on
  the target (`trustFolders`, `providerInstance/update`); turning it off stops the marking and
  removes nothing already marked.

### Window

#### The tray

YAAC keeps an icon in the system tray (D127; Windows — no tray is built on Linux, and WSLg has
no StatusNotifier host to show one). **"Keep running in the tray when closed"** is **on by
default** (P70). With it on, the title bar's close button and Alt+F4 **hide** the window: it
leaves the taskbar, runs no egui pass and paints nothing, and wakes only when something asks
for a repaint (a hub message, a tray click) — so it costs no CPU while nothing happens. The
tray icon's **left click** (or double click) shows the window and brings it to the front; its
**right-click menu** has **Open YAAC** and **Quit**. Quit closes the window process; the hub
runs on, as it always does when the window closes. With the option off — or where there is no
tray icon — closing quits, as before.

The icon is the app icon. While some thread needs the user it carries a **small red badge**
and its tooltip reads **"YAAC · N need you"** (otherwise "YAAC"); the count is the Needs-you
list's, kept up to date while the window is hidden.

**One window per user session** (P71). Starting `yaac` while a window is open — perhaps hidden
in the tray — shows that window and exits. On Windows this is a named event in the session's
`Local\` namespace, named after the hub's pipe (so a test profile has its own): the first
window waits on it on a thread of its own; a second `yaac` signals it, lets the first take the
foreground, and exits. The demo (`--demo`, `--screenshots`) is not limited.

## Rendering and memory

The UI must stay small and idle at zero CPU. The rules that make that true:

- **Repaint only on demand.** egui runs reactively. The I/O thread calls `request_repaint`
  when visible state changes, and coalesces a burst of stream events into one repaint per
  display frame.
- **Virtualise both lists.** The sidebar and the transcript lay out only visible rows. Item
  heights are measured once and cached until width or content changes.
- **Parse markdown once.** A completed item keeps its parsed blocks and laid-out text. While an
  item streams, only a bounded tail is re-parsed each frame — never the whole item, which would
  grow quadratically on a long answer or an unclosed code fence. When the item completes it
  gets one final, exact parse.
- **Cap what one item can cost.** A single 20 MB tool output must not become 20 MB of laid-out
  text. Large items show a bounded head and tail with "show more", fetched on demand.
- **Keep the reader's place.** Scroll position is anchored to an item and an offset within it,
  so a window resize, a font change, or content arriving above does not move what the user is
  reading.
- **Keep transcripts out of memory.** Only open threads hold items in memory, plus a small
  least-recently-used set. The sidebar holds summaries only.
- **Images at display size.** Decode to thumbnail resolution, upload to a GPU texture, drop the
  pixels. Textures are evicted least-recently-used.
- **Load syntax highlighting lazily**, per language, the first time a code block needs it.
- **Never block the UI thread — or the I/O thread.** Connection work happens on the I/O thread;
  disk writes, hashing, and image decoding happen on a small bounded worker pool; the UI reads
  snapshots.

## Accessibility

egui exposes an accessibility tree through AccessKit. The thread tree, request cards, and
composer controls carry names and states, approvals and questions are fully operable from the
keyboard, and focus moves predictably when a request arrives (it is announced; it does not
steal focus from what the user is typing).

## Keyboard

Every key the window handles is a command in **one table** (`yaac-core`'s `commands`), listed
in full — name, explanation, default key — in [the command catalogue](plan/commands.md). The
**Commander** (default Ctrl+Space, D130) searches it; **Settings → Keyboard** rebinds it (D131);
one dispatcher in the window resolves every global key through it. Three rules come first,
because they prevent expensive mistakes:

- **Approval keys act only while that card has focus.** Enter in the composer sends a message;
  it never approves something further up the page. Enter, Shift+Enter, Ctrl+Enter and Esc stay
  with the composer, and Enter and Esc with the focused card; they are listed but not
  rebindable (P76). The Commander's *Allow* and *Deny* act only on the card that had focus
  when it opened (P78).
- **A request that arrives while the user is typing does not take focus.** It is announced —
  the Needs-you count changes and a one-line notice appears above the composer — and the caret
  stays where it was.
- **Plain keys never fire in a text field.** A key without Ctrl or Alt (F2, Delete) acts only
  when focus is in the list or the thread view; the keys text editing uses (Ctrl+Delete,
  Ctrl+A, Ctrl+←…) stay with the field (P77).

**Ctrl+J** (like the Needs-you button, D117) opens the next thread that needs the user,
scrolls to the request, and focuses its card; pressing it again moves to the next one. Hover
texts and notices show each command's key as currently bound.

### The Commander

A centred overlay over a dimmed window (screens 64–66): a search field, then the list in the
shared menu style. Each row is the command's name, its one-line explanation in the secondary
colour (or, when it cannot run now, the reason), and its key on the right in a key cap. With
nothing typed the list starts with *Recent* and then every group of the catalogue; typing
filters and ranks (P80). ↑/↓ move, Enter runs, Esc closes, a click outside closes. A command
that takes an argument continues inside it: the step's name sits before the field and the list
becomes its choices (models of this harness, effort levels, modes, mute durations, orders,
grouping, theme, targets, related agents, history, settings pages); Esc or Backspace on an empty
field goes back. Dialogs that exist (fork, delete, archive, create PR, mute until a date) open
as before. The Commander draws only when a frame happens anyway — its caret does not blink — so
it costs nothing while open.

**A thread the Commander opens is ready to type in** (D149, P171): choosing a thread (*Find a
thread…*, *Go to a related agent…*, *History…*) or running a command that goes to one (*Next
thread that needs you*, *Next unseen finished thread*, *Next/Previous thread in the list*,
*Back*, *Forward*, *Go to the parent thread*) leaves the caret in that thread's composer. The
same commands run by their keys do it too, when the key still works with the caret in a text
field (a plain key pressed again must reach the command, not the draft). Only when the composer
can be typed in: a thread in use elsewhere (read-only), one on a stopped distro, one whose
composer is dimmed by a request waiting for an answer, and one whose card has the keyboard keep
today's focus. Clicking a sidebar row does not move the caret.

### Settings → Keyboard

Every command, grouped as in the catalogue (screen 67): name and explanation on the left, the
key cap, **Clear** and **Reset** on the right; **Reset all** at the top. Clicking the key cap
records the next chord (Esc cancels, Backspace or Delete clears). A chord another command has
is flagged under the row — "Ctrl+K is used by Search threads." — with **Replace** and
**Cancel**; a chord a local key uses is refused. Ctrl+Space carries a note about input-method
layouts (P81). Only differences from the defaults are stored, as the window preference
`keyBindings`.
