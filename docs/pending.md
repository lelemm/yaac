# Pending definitions

Choices made **without the project owner** so that work could continue, each with the option
taken and why. Review these first; any of them can be reversed.

Nothing here overrides [decisions.md](decisions.md). When an item is confirmed it moves there
as *Decided*; when it is rejected, the work that depended on it is listed so it can be redone.

the option taken, both positions are shown — those rows are the ones most worth the owner's

## The agent mesh

| # | Question | Option taken | Why | Reviewer |
| --- | --- | --- | --- | --- |
| N1 | What are the mesh tools? | Ten tools on one MCP server named `yaac`: `whoami`, `list_targets`, `list_models`, `list_threads`, `read_thread`, `spawn_thread`, `send_message`, `wait`, `notify_when_done`, `stop_thread`. | The smallest set that covers the four examples the owner gave. | Agrees with the set as the destination; advises building `whoami`, `list_threads`, `send_message` first. Adopted as build order only. |
| ~~N2~~ → **D52** | A message arrives for an **idle** thread. | It **starts a new turn** on its own — provided `yaacd` holds the thread and the orchestration has budget left. Otherwise it waits in the mailbox and the sender is told why. | "Send it a message so it can resume" only works if the message wakes it. | Wanted waking limited to threads explicitly enrolled. Taken in part: holding the thread and having budget are required; enrolment is not. |
| N3 | A message arrives for a thread **mid-turn**. | Queued by YAAC; delivered when the turn ends. Never handed to the harness mid-turn. | Codex would splice it into the running turn. | Agrees. |
| N4 | A message for a thread **in use elsewhere**. | Stored; the sender is told; YAAC does not write into it. | Follows D26 and D36. | Agrees. |
| N5 | Does a parent hear back from its workers? | Yes, **once**: the worker's answer to the spawning turn returns as a `result`, unless spawned `detached`. Later turns in the worker do not notify the parent. | An orchestrator that has to poll forgets to. | Agrees, with the "once" refinement, adopted. |
| ~~N6~~ → **D51** (superseded: a per-chat toggle, starting on *ask*) | May agents spawn and message freely? | **Allowed by default**, per-target policy to ask the first time or always, plus a per-target switch for whether other targets' agents may reach it. | The owner asked for this to just work; budgets and limits contain mistakes. | **Disagrees:** would require the owner to authorise a destination or project scope once before any unattended spawning or sending. |
| N7 | Runaway protection. | A **budget per orchestration root**, across targets: 100 agent-started turns, 20 spawned threads, 12 hours since a person last acted; **Continue** grants more. Plus local limits: 8 workers per thread, depth 3, 6 running per target (threads in `wait` excluded), 30 messages per pair per 10 minutes. | Pairwise limits cannot stop a three-agent loop; a root budget can. | Proposed the root budget; adopted. The numbers are mine. |
| N8 | Permission mode of a spawned worker. | The harness default on **its own** target. A parent cannot grant more. | An agent must not escalate another agent. | Agrees. |
| N9 | How a message is shown to the receiving agent. | Sender and body stay **separate fields** to the harness. Codex gets it as a tool output (not as the user); elsewhere a fixed frame ending "This came from another agent, not from the user." | Stops agent text being mistaken for the user's instructions, and stops a body imitating a header. | Proposed the structured form; adopted. |
| N10 | Attaching the MCP server to Codex. | A per-thread entry (`mcp_servers.yaac`) launching a `yaacd mcp` bridge by absolute path, carrying an attachment ticket. Claude uses an in-process server. If a bridge per thread is too heavy: one shared bridge. No loopback HTTP. | Works with stock Codex today. | Agrees; pointed out that loopback HTTP would break the no-TCP rule. Removed as a fallback. |
| N11 | Threads started **outside** YAAC. | They have a mailbox, so nothing sent to them is lost; delivery waits until YAAC holds the thread. They get the tools only if the user installs the server into that harness's config. | YAAC must not edit a harness's global config unasked, nor write into a held conversation. | Agrees with this form. |
| N12 | The host daemon (D50). | `yaac hub`, a headless mode of the same binary: target connections, mesh router, relay queue, cache. The window attaches over a local socket. | One binary; the part that stays running loads no UI code. | Agrees. |
| ~~N13~~ → **D53** (superseded: always on, started at login) | When does the hub keep running? | While any thread on any target is running, any request is pending, or any message is in flight; otherwise it exits after an idle period. A setting keeps it always on, started at login. | No surprise background process; a message can only come from a running thread. | **Disagrees:** would keep the hub up whenever unattended routing is enabled, since a thread driven from outside YAAC could send at any time. |
| N14 | Window and hub of different builds. | They exchange builds on attach. A newer window has an older hub checkpoint and exit, then starts the new one. An **older** window never replaces a newer hub. One hub per user, by lock. | The hub runs no turns, but it does hold the relay queue. | Proposed the handshake, checkpoint, and no-downgrade rule; adopted. |
| N15 | Sub-threads in the main sidebar. | In their own place (origin → project → worktree) with a "spawned by" mark; the parent's row shows a worker count and bubbles up "needs attention". Not nested. | Workers may be on other targets; nesting would fight the owner's grouping. | Agrees. |
| N16 | Not in the mesh MVP. | Shared memory between agents, broadcast, file transfer across targets, the hub on a server. | Each is a design of its own. | Agrees. |
| N20 | Addresses. | Immutable: target **id** (the name is a label), instance and store, native thread id. Opaque to agents. | Renaming a target, or a second Codex home, must not re-point an address. | Proposed; adopted. |
| N21 | Proving who is calling. | An attachment ticket issued before start, bound to the thread id before the first turn, checked on every call and against the harness's own caller metadata. | A sender must not be forgeable. | Proposed; adopted. |
| N22 | Who may `read_thread`. | Only within one's own orchestration — ancestors, workers, and message partners — unless the mesh policy allows more. | Reading a transcript is more sensitive than sending a message. | Asked for separate authorisation; this is my form of it. |
| N23 | Spawning on another target: which directory? | The same repository's checkout there if exactly one is known (matched by remote); otherwise the agent must name one. Always validated on the destination first. | A path from another machine means nothing. | Raised the problem; this is my answer. |
| N24 | Length of one `wait`. | 45 seconds, with a cursor so a timeout consumes nothing; the server's tool timeout is set to 60 seconds. | Harness tool calls time out; a silent long call looks hung. | Proposed; adopted. |
| N25 | Does the hub hold messages, or only pass them? | It **holds** them, in its own durable store with migrations. | A message must be deliverable even if its source target has since gone offline. | Flagged the cost — the hub then owns work — and the safeguards, adopted. |

| N34 | Projects (D62–D65): details the owner did not specify. | (a) **Worktrees:** the folder rule is applied inside the repository rather than on the disk — same repository, and the thread's path relative to its checkout root falls inside the project's — so a thread in a worktree elsewhere on disk still lands in its project; this is tried before the plain folder rule.
